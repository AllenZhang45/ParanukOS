# ParanukOS 用户态 —— Milestone 4 接口

[English](user_mode.md) | [中文]

> **状态：接口提案，尚未开始实现。**
>
> 前置条件：M0–M3 已实现并验证通过（[kernel_interface_CN.md](kernel_interface_CN.md)、
> [memory_subsystem_CN.md](memory_subsystem_CN.md)、[threads_and_scheduling_CN.md](threads_and_scheduling_CN.md)）。
> 本文档定义 M4：**第一个用户态服务 —— 最小特权切换与系统调用 ABI，暂无 IPC 语义**。

## 1. 范围

### 1.1 本文档定义什么
* `BootInfo` **v1**：追加的用户镜像字段，以及内核如何继续兼容 v0（§3）
* 引导器如何装载第二个 ELF、内核如何把它映射进用户地址空间（§4）
* 用户地址空间：用户虚拟地址放在哪里、为什么必须在恒等映射之上、页表里如何表达
  supervisor/user 分离（§5）
* 用户代码/数据段描述符，以及让 CPL 3 → CPL 0 落在合法内核栈上的 `TSS.rsp0` 规则（§6）
* 特权切换：用户线程保存的帧长什么样、由谁构造（§7）
* 系统调用 ABI（`int 0x40`）：寄存器约定、M4 的调用表，以及**指针校验**——本项目第一个真正的
  安全边界（§8）
* 用户态故障：内核如何区分"服务崩了"与"内核崩了"（§9）
* 用户程序及其极小的库，各自带链接脚本（§10）
* 退出码 47、M4a/M4b 拆分与可否证的验收标准（§11）

### 1.2 本文档不定义什么
IPC 与能力令牌（M5）、多于一个地址空间或多于一个用户线程、按需分页、ELF 重定位/动态链接、
文件系统式程序装载、`syscall`/`sysret`、信号、进程树、服务间共享内存。内核**保持当前的
低地址恒等映射链接地址**：**迁到高半区明确不属于 M4**［决策 #41］。

### 1.3 术语

| 术语 | 含义 |
|---|---|
| CPL | 当前特权级（0 = 内核，3 = 用户） |
| 用户地址空间 | 一个 PML4：低半部分是内核的恒等映射（仅 supervisor），用户区可被用户访问 |
| 用户区 | 用户代码/数据所在的虚拟地址区间 `[USER_BASE, …)` |
| 系统调用 | 经 `int 0x40` 完成的 CPL 3 → CPL 0 切换 |
| 服务 | M4 运行的那一个用户态程序 |
| `TSS.rsp0` | CPL 3 → CPL 0 切换时 CPU 换过去的内核栈 |

## 2. 基线与前置条件

M4 建立在 M3 的线程、GDT/TSS/IST、中断基础设施与调度器之上。不得破坏：

* M0–M3 的退出码含义不变（33/35/37/39/41/43/45）；**47** 是新增；
* 内核线程的行为完全不变：M4 只是新增了一种**线程种类**，不替换调度器——同一个轮转队列、
  同一条切换路径、同一个六步自检；
* IDT 的向量保持不变：0x20 时钟、0x30 让出、0x31 退出；M4 新增 **0x40 系统调用**；
* 读 `BootInfo` v0 的代码继续可用（v1 是超集）。

## 3. `BootInfo` v1（按 `kernel_interface_CN.md` §5.5 只追加）

追加四个字段；`version` 变为 1，`size` 变为 **120**（v0 的 88 + 32）。不删除、不移动、不改变
任何已有字段的含义。

```rust
#[repr(C)]
pub struct BootInfo {
    /* v0 字段，保持不变：0..88 */
    pub user_phys: u64,   // 88：已装载用户镜像的物理起始地址
    pub user_size: u64,   // 96：字节长度（页对齐区间）
    pub user_vaddr: u64,  // 104：与 user_phys 对应的虚拟地址
    pub user_entry: u64,  // 112：用户入口点（镜像内的一个虚拟地址）
    // size = 120，version = 1
}
```

* `validate()` **同时接受两个版本**：要求 `magic` 匹配、`size` 至少 88；只有
  `version >= 1 && size >= 120` 时才读用户字段［决策 #42］。v0 意味着"没有用户载荷"，此时内核
  跳过 M4 部分的自检并带着明确信息报 47，而不是半初始化地继续启动；
* `user_vaddr` 让内核不必解析 ELF 就能映射镜像：引导器取第一个 `PT_LOAD` 段的
  `(p_paddr, p_vaddr)` 差值，于是整段页对齐的物理区间就映射到
  `[user_vaddr, user_vaddr + user_size)`——形状上是恒等映射，但落在用户区［决策 #43］；
* 引导器用**与内核镜像完全相同**的规则装载 `\EFI\PARANUKO\USER.ELF`
  （`crates/kernel-image`：ELF64、小端、`ET_EXEC`、段不重叠、入口落在可执行段内）。用户镜像缺失
  或非法即**装载失败 → 35**，与内核镜像缺失完全一致——M4 不存在"有内核但没有服务"的有意义模式。

## 4. 用户程序的镜像

* 它是独立 crate（`crates/user`），为 `x86_64-unknown-none` 构建，**链接在 `USER_BASE`**；
* 它的链接脚本把 `.text`/`.rodata`/`.data`/`.bss` 放在用户虚拟地址上，并用 `AT(…)` 为每个段
  显式指定物理装载地址，于是 `p_vaddr` 是用户虚拟地址而 `p_paddr` 仍在 4 GiB 以下（引导器依旧按
  `p_paddr` 装载，见 `kernel_interface_CN.md` §3.2）［决策 #44］；
* 与内核一样是**静态、非 PIE**（`-C relocation-model=static`），不做重定位处理；
* `crates/user-lib` 放系统调用的包装函数（`write`、`exit` 等），让程序源码保持可读，并让这个 ABI
  只有一份定义、两侧共用；
* 程序入口是 `_start`（内核并不会盲目使用 `e_entry`：它把 `user_entry` 填进初始用户帧的 `rip`）。

## 5. 用户地址空间

### 5.1 布局

| 区间 | 内容 | 权限 |
|---|---|---|
| `[0, 4 GiB)` | 内核既有的恒等映射（内核镜像、堆、页帧、栈、BootInfo） | 仅 supervisor（`U/S = 0`） |
| `[USER_BASE, …)`，`USER_BASE = 0x1_0000_0000`（4 GiB） | 用户镜像、它的栈，日后它的堆 | 用户（`U/S = 1`），暂未禁用可执行 |

`USER_BASE` 刻意就取内核恒等映射的终点（`memory_subsystem_CN.md` §3.4，
`MAX_IDENTITY_BYTES = 4 GiB`）［决策 #45］。把用户虚拟地址放进恒等映射区间内，就必须覆盖内核
自己可能正在使用的物理内存的恒等表项——内核会失去对自己页帧的访问。起点放在映射之上，让两种角色
在构造上互不相交，同时内核仍可通过**物理地址**（恒等）读取用户内存，用于校验或替服务拷贝。

### 5.2 页表

* M4 只有**一个**地址空间，而且就是**当前这一个**：用户区的表建在与内核表**同一个竞技场**里
  （`USER_BASE = 4 GiB` 落在 `PDPT[4]`，内核自己的 PDPT 正好空着），因此 **M4 从不写 `CR3`**
  ［决策 #54］；
* 推论：没有按线程的地址空间需要切换，也没有 TLB 管理。把服务挡在内核内存之外的是 `U/S` 位，
  而不是另一张表——§10 的反例正是让这条主张可被否证的；
* 被否决的方案（每个地址空间一张新 PML4）在 `USER_BASE = 4 GiB` 下是**自相矛盾**的：4 GiB 的
  PML4 索引是 0，共享第 0 项会让「独立」地址空间映射到与内核**完全相同**的地址，抽象就是假的。
  真正的分离要么把 `USER_BASE` 抬到 512 GiB 以上（有自己的 PML4 项），要么整套按进程的布局——
  **共享**而不是复制，日后新增的内核映射自动出现在每个地址空间里［决策 #46］。第 1..512 项除用户
  区外为空；
* 用户页是 **4 KiB**（用户区用 PT 映射，而不是 2 MiB 大块），因为 M4 需要按页控制 `U/S`，而且
  `.text` 与 `.data` 最终需要不同的权限；
* **页表链路的每一级都必须带 `U/S = 1`**，不只是叶项［决策 #55］。中间层缺位时 CPU 会在**叶项的
  地址上**报保护违例（`#PF`，`error_code` 第 0 位与第 2 位置位）——真机上就是这么发现的。给中间层
  置位并**不会**扩大可达范围：用户可访问的中间层之下，若叶项是 supervisor，CPL 3 依然碰不到，
  这正是内核的 2 MiB 恒等大块保持私有的原因；
* 运行期内核不通过走页表去"推导"用户指针，除了 §8 的校验：它通过在当前地址空间的用户区里查找来
  验证一个用户指针；
* 构建逻辑放在 `crates/kernel-memory`（宿主单测），存储由内核提供——与本项目其它页表构建器一致。

### 5.3 服务能做什么、不能做什么
* 只能读写执行自己的区间；访问 `[0, 4 GiB)` 一律故障（`#PF`，`U/S` 违例），即便那些地址在它的
  页表里是 present 的；
* 不能关中断、不能安装描述符、碰不到设备：CPL 3 执行 `in`/`out` 会触发 `#GP`，也没有任何
  MMIO 被映射为用户可访问；
* 不能分配内存：M4 没有内存系统调用；镜像的 `.bss` 加上一段固定的用户栈就是它拥有的全部
  ［决策 #47］。内存系统调用需要一套真正的所有权模型，属于 M5 的能力工作。

## 6. 描述符与中断用的内核栈

* M3 的 GDT 已经为 M4 预留了三个槽位；M4 填其中两个：**用户代码 `0x28`** 与**用户数据 `0x30`**，
  都是 `DPL = 3`、平坦、长模式（代码段 `L = 1`）；
* 用户帧使用 `cs = 0x28 | 3 = 0x2B` 与 `ss = 0x30 | 3 = 0x33`（RPL 3——`iretq` 要求帧里选择子的
  RPL 与 CPL 一致）；
* **`TSS.rsp0` 必须在任何 CPL 3 代码运行之前指向"当前用户线程"的内核栈顶**，并在每次切换到用户
  线程时刷新［决策 #48］。否则用户态里发生时钟中断时，压栈会落在 `rsp0` 仍然指着的旧栈上——内核
  正是这样在很久之后才以诡异方式崩掉的。因此 `switch_to` 在被换入线程是用户线程时设置 `rsp0`
  （内核线程可以不动它）。

## 7. 特权切换

切换路径不需要任何新东西：用户线程就是一个普通的 M3 线程，只是它保存的帧恰好带 CPL 3 的选择子
［决策 #49］。

* 服务的初始帧按内核线程的方式构造（M3 附录 §14.5），但字段不同：
  * `rip = BootInfo.user_entry`、`rsp = 用户栈顶`（用户区里的一个虚拟地址）；
  * `cs = 0x2B`、`ss = 0x33`；
  * `rflags = 0x202`（`IF = 1`，第 1 位置位）；
  * `rdi`/`rsi` = 一个小的参数块（M4 里程序可以忽略）；
* `iretq` 完成 CPL 0 → CPL 3 的切换，并从帧里加载用户 `rsp`——这正是用户帧必须携带**用户**栈指针、
  而内核线程帧不需要的原因；
* 用户栈是启动时从页帧分配器取的若干页，映射在 `USER_BASE + offset`、用户可写，最低字照例放 M3
  的金丝雀；
* 当时钟抢占用户代码时，CPU 切到 `TSS.rsp0`（该线程的内核栈）、在那里构造帧，既有 ISR 路径把它
  保存下来——调度器随后把它当作普通线程处理。因此 `Context.rsp` 在用户态与内核态下都指向一个
  `IrqFrame`。

## 8. 系统调用 ABI（`int 0x40`）

* 向量 **0x40**，**`DPL = 3` 的中断门**，使 CPL 3 可以执行 `int 0x40`；处理器复用 M3 的
  `irq_common` 路径（同一个帧、同一个返回协议）。不碰任何 MSR：`syscall`/`sysret` 是后续优化
  ［决策 #50］；
* 寄存器：`rax` = 调用号，`rdi`、`rsi`、`rdx`、`r10`、`r8` = 参数，`rax` = 返回值（处理器直接改写
  帧里的 `rax` 槽，因此不需要另立一套约定）；
* M4 的调用表（刻意很小）：

| # | 调用 | 参数 | 返回 |
|---|---|---|---|
| 0 | `exit` | `rdi` = 状态码 | 永不返回；线程被标为 `Exited` |
| 1 | `write` | `rdi` = 用户指针，`rsi` = 长度 | 已写字节数，或 `-1` |
| 2 | `yield` | — | 0 |

* **指针校验**（本项目第一个真正的安全边界，［决策 #51］）：`write` 必须 (a) 拒绝超过
  `WRITE_MAX` 的长度（固定上限），(b) 检查 `ptr` 与 `ptr + length` 是否溢出，(c) 通过页表验证该
  区间涉及的**每一页**在当前地址空间里都是 present 且用户可访问——绝不"相信"指针本身。由于用户
  虚拟地址与恒等映射不相交（§5.1），"这个虚拟地址是否落在用户区"是最便宜的第一道检查；
* 违例即**杀掉服务**（线程标为 `Exited`，内核记录原因）并报告为用户态故障（47），而不是内核
  panic：有 bug 的服务不能把内核带下去［决策 #52］；
* 系统调用在中断关闭下运行（中断门已清 `IF`），且不得阻塞；M3 那条"中断处理器里不分配内存"的
  规则同样适用于系统调用路径；
* 系统调用处理器是一条**内核**路径，它可能触碰用户内存；校验通过后它通过恒等映射访问——那正是
  同一块物理内存。

## 9. 用户态故障 vs 内核故障

异常处理器本来就能拿到被中断的 `cs`；若其 RPL 为 3，故障来自服务［决策 #53］：

* 与内核故障一样打印完整信息（`rip`、`error_code`，`#PF` 还要 `cr2`），外加线程号；
* 把服务的线程标为 `Exited`，在 M4 自检结束时报告 **47**；
* CPL 0 的故障仍然意味着"内核崩了" → **41**。这个区分让日志保持诚实，也是两个退出码存在的理由。

## 10. 用户程序（M4 的证据）

程序刻意做得很小，但覆盖了每一件事：它通过 `write` 系统调用打印一行固定文本、调用一次 `yield`
（证明 CPL 3 线程与别的线程一样被调度），然后 `exit(0)`。内核自检观察：

1. 服务确实到了 CPL 3（至少有一次从 `cs = 0x2B` 进入系统调用路径）；
2. 它的 `write` 输出逐字节出现在串口日志里；
3. 它至少被抢占过一次（它运行期间 M3 的 tick 计数在推进）；
4. 它退出了、栈被回收，页帧数回到服务创建之前的值；
5. 注入的坏指针（例如恒等映射区里的 `0x100000`）被**拒绝**、服务被杀、内核报告 47——证明校验
   真的在工作的反例。

两个仅测试特性让反例可以被触发：

| 特性 | 效果 | 期望 |
|---|---|---|
| `inject-user-bad-pointer` | 程序用一个内核虚拟地址调用 `write` | 内核拒绝、杀掉服务 → **47** |
| `inject-user-fault` | 程序解引用一个未映射的用户虚拟地址 | CPL 3 触发 `#PF` → 处理器认定为用户故障 → **47** |

## 11. 交付、交付物与验收标准

### 11.1 拆分

| 部分 | 内容 | 为什么 |
|---|---|---|
| **M4a** | `BootInfo` v1 + 引导器装载 `USER.ELF` + 用户 crate/链接脚本 + `AddressSpace` + 用户线程 + 特权切换（程序能跑、能故障/退出；尚无系统调用） | 这些是"系统调用值得存在"的前提；页表或 `rsp0` 出错会表现为三重故障或静默损坏 |
| **M4b** | `int 0x40` + 调用表 + 指针校验 + 用户故障上报 + 自检与两个注入特性 + 冒烟用例 | 建立在已经证明过的 CPL 3 切换之上；这个 ABI 小到可以作为一个整体审阅 |

### 11.2 交付物
`crates/kernel-memory`（地址空间构建器 + 宿主单测）、`crates/boot-info`（v1 + 测试）、
`crates/kernel-image`（不变，用户镜像复用）、`crates/user` + `crates/user-lib`、
`crates/kernel/src/user.rs`（特权切换、系统调用表、校验）、`crates/kernel/src/gdt.rs`（用户描述符）、
`crates/kernel/src/sched.rs`（切换时设置 `rsp0`）、`crates/kernel/src/idt.rs`（向量 0x40 + CPL 过滤）、
`src/bootloader/`（装载第二个 ELF）、`tests/smoke.sh`、本文档双语、`kernel_interface_CN.md`
（§5.5 说明、§7.2 退出码、§9）、README。

### 11.3 验收标准 —— 逐条可机器校验（M4a 除注明处均已满足；M4b 尚未开始）
- [x] `BootInfo` v1 为 120 字节，且 v0 前缀逐字节不变（单元测试钉住每个偏移）；
- [x] 引导器报告用户镜像的物理区间、虚拟基址与入口；`USER.ELF` 缺失或非 ELF 一律以 **35** 拒绝；
- [x] 内核打印地址空间：`user: 0x…→0x… (N 页, U/S=1)，入口 0x…`，以及切换时的 `rsp0`；
- [x] 服务运行在 CPL 3（日志里至少出现一次 `cs=0x2B`），且它的 `write` 输出出现在串口日志里；
- [x] 它至少被抢占一次，退出后栈被回收（页帧数回到基线）；
- [ ] `inject-user-bad-pointer` → **47**，日志指出被拒绝的虚拟地址；
- [ ] `inject-user-fault` → **47**，`cr2` 指出故障地址，而**不是** 41；
      **（被阻塞）** 该变体只有加 `-C code-model=large` 才链接得过（`.rodata` 引用需要
      `R_X86_64_64`，默认 small 代码模型发 `R_X86_64_32S`），但加了之后普通构建的 ELF 变成
      「入口不落在可执行段内」，因此先回退；47 这条路径本身已在真机验证（见下方日志）。
- [x] CPL 0 的故障仍然报 **41**（M1/M2/M3 的反例无回归）；
- [x] `cargo test -p kernel-memory -p boot-info …` 通过；fmt/clippy 在所有配置下干净；
- [x] `check_kernel_elf.py` 仍通过，内核镜像仍在 `MAX_KERNEL_PAGES` 之内。

| # | 坑 | 对策 |
|---|---|---|
| 1 | 没有按线程更新 `TSS.rsp0` → 用户态中断压到旧栈上 | 在 `switch_to` 里对被换入的用户线程设置它（§6），并在自检里断言 |
| 2 | 用户页忘了 `U/S = 1` → 服务在第一条指令取指时就死 | 构建器给每个用户叶项置 `USER`；自检的第一行日志就来自 CPL 3 代码 |
| 3 | 内核页留着 `U/S = 1` → 用户代码能读内核内存 | 内核恒等映射在 M2 就以 `U/S = 0` 建立并被共享、从不复制；坏指针注入证明拒绝是有效的 |
| 4 | 帧里的选择子 RPL ≠ 3 → `iretq` 在 CPL 0 触发 `#GP` | `cs = 0x2B`、`ss = 0x33`，并由针对帧构造的单元测试钉住 |
| 5 | 相信用户指针 | §8 的三道检查 + 反例注入 |
| 6 | 用户程序的段按 `p_paddr` 装载、却用错误的差值映射到 `p_vaddr` | 引导器用第一个段算出 `user_vaddr`，内核用同一个差值映射整段（§3） |
| 7 | 用户镜像的 `.bss` 没清零 | 引导器按内核镜像同样的步骤清零（`kernel_interface_CN.md` §3.2 第 3.4 步） |
| 8 | 用户故障被当成内核崩溃上报 | §9 的 CPL 判定 |

## 12. 决策记录

| # | 决策 | 结果 | 理由 | 可逆性 |
|---|---|---|---|---|
| 41 | M4 保持内核低地址恒等映射的链接地址；用户虚拟地址放在恒等映射之上 | 内核本身不改链接脚本/引导器装载规则 | 高半区迁移会牵动链接脚本、装载规则、内核里每个裸地址与 49 条冒烟断言；M4 的目标是特权切换，不是内存布局改造 | 中（高半区仍然可走：按 `p_paddr` 装载、按 `p_vaddr` 映射） |
| 42 | `BootInfo` v1 追加四个 `u64`；`validate()` 同时接受 v0 与 v1 | size 120，version 1 | 真正演练"只追加"的演进流程；v0 启动意味着"没有服务"，内核如实报告而不是半启动 | 高 |
| 43 | 引导器同时告诉内核镜像的物理区间**与**虚拟基址，内核不需要 ELF 解析器 | 整段一个差值 | 让 ELF 知识只存在于一处（`kernel-image`，引导器使用），内核的映射算术保持平凡 | 高 |
| 44 | 用户程序链接在 `USER_BASE`，用 `AT(…)` 指定物理地址 | `p_vaddr` 高、`p_paddr` 低 | 引导器按 `p_paddr` 装载、内核把物理页映射到用户虚拟地址——两侧都不必改动 | 中 |
| 45 | `USER_BASE = 0x1_0000_0000`（4 GiB，正好是恒等映射的终点） | 构造上互不相交的虚拟地址空间 | 用户地址若落在恒等区间内，会覆盖内核自己正在使用的物理 RAM 的映射 | 高 |
| 46 | M4 只有一个 `AddressSpace`；其 PML4 共享内核的低端 PDPT | 日后可有多个 | 按线程的地址空间是 M5 形态的问题（所有权与共享）；共享第 0 项还能保证内核映射不会在各空间之间漂移 | 高 |
| 47 | M4 没有内存系统调用 | 服务只有镜像 + 一段固定栈 | 没有所有权/能力模型的分配，到 M5 反正要重新设计 | 高 |
| 48 | 每次切到用户线程都刷新 `TSS.rsp0` | `switch_to` 里一次写入 | 陈旧的 `rsp0` 会让用户态中断踩坏它指向的栈 | 高 |
| 49 | 用户线程就是普通的 M3 线程，只是帧里带 CPL 3 选择子 | 完全不新增切换路径 | 既有的基于帧的切换本来就携带 `cs`/`ss`；再加一套机制就是 M3 那个"两种形状"的错误 | 高 |
| 50 | 系统调用经 `int 0x40` 进入 | `DPL = 3` 中断门，复用 `irq_common` | 不需要配 MSR，与其它一切共用一条代码路径；`syscall`/`sysret` 是可测量的后续优化 | 高 |
| 51 | 内核接触任何用户指针之前都要对着地址空间校验 | §8 的三道检查 | 这是第一个真正的信任边界；"用户传了个指针"绝不能等于"内核去解引用它" | 高 |
| 52 | 非法系统调用参数或用户故障 → 杀掉服务并报 47 | 服务死、内核活 | 服务的 bug 不能把内核带下去，日志也不能把它叫成内核崩溃 | 中（47 一旦发布即冻结） |
| 53 | 异常处理器按帧里的 CPL 决定 47 还是 41 | 同样的诊断，两个退出码 | 让"谁崩了"仅凭退出码就能回答 | 高 |
| 54 | M4 把用户区建在与内核**同一个**页表竞技场里，从不切换 `CR3` | 单一地址空间；隔离完全由 `U/S` 位承担 | `USER_BASE = 4 GiB` 的 PML4 索引是 0，「独立」PML4 共享第 0 项只会映射到完全相同的地址，是假抽象。多地址空间（以及随之而来的 `CR3` 切换）属于引入它们的里程碑 | 高 |
| 55 | 用户映射的每一级都带 `U/S = 1`；可达性只由叶项决定 | 每个表项多一个标志位 | CPU 要求每一级都有该位，否则访问故障（真机上是 `#PF` `error_code=0x15`）；而 supervisor 的叶项仍然让内核不可达 | 高 |
| 56 | 用户镜像链接在 `USER_BASE` 加一页处（`FILEHDR` 头部正好从 `USER_BASE` 开始），并用统一的 `AT(ADDR(段) - USER_DELTA)` | 整个镜像一个 `PT_LOAD` 差值 | 引导器用**一个**差值映射镜像（`BootInfo.user_vaddr`），两侧必须一致；头部并进 `.text` 可避免第二个 `PT_LOAD` 的 `p_paddr` 等于其用户虚拟地址 | 中 |

## 13. 接口变更流程
1. `BootInfo` v1 遵循 `kernel_interface_CN.md` §11：只追加、`version`+1、`size` 变大；同一改动里
   同时更新两种语言与 ABI 两侧。
2. 系统调用 ABI（§8）是 ABI：改动它必须同时改 `crates/user-lib`、内核的分发表与本文档。
3. `crates/kernel-memory` 的地址空间构建器有宿主单测；改动必须配套测试。
4. 双语文档：每次改动必须同时更新本文件与 [user_mode.md](user_mode.md)。
5. 实现状态：每完成一部分，更新 §11 与 `kernel_interface_CN.md` §9 的 M4 行。
